第一块：空置域挖掘（命令版"世吞"）
---------------------------------------------------------
一句话：小服务器真造世吞（几万格 TNT + 上万实体）会先把自己拖死，
于是给管理员另一条路 —— 对角选两点，服务端用原版 /fill 分三阶段把区域挖成空置域。

命令（都在 /hy clear 下，权限门槛单独更高）：
  /hy clear <x1> <z1> <x2> <z2>  ★最常用：对角两点直接建选区，选完自动预演
  /hy clear <x2> <z2>            以你当前所站位置为角点 1、参数为角点 2
  /hy clear <边长>               以你为中心的方形（/hy clear 100 = 挖 100x100）
  /hy clear pos1 | pos2 [x z]    一个角一个角地选（不带坐标 = 取当前所站位置）
  /hy clear dim <维度>           控制台/RCON 指定目标维度（the_nether / the_end，支持简写）
  /hy clear preview              单独再预演（**一条命令都不派发**）
  /hy clear go                   开始挖（= start confirm；预演里还有可点击的「确认开始挖掘」）
  /hy clear status | stop | reset

省事写法（按"命令都要方便直观"定的形式）：
  名单: /hy add ex  <名字> [名字…]    加入外置（批量＝空格隔开）
        /hy add off <名字> [名字…]    加入离线：先查户口，有历史身份就**沿用**，没有才发 UUIDv7（并查重）
        /hy off <名字> [名字…] force  给已有玩家换一个全新 UUIDv7（老存档的背包/成就不跟过去）
        /hy del <名字> [名字…]        按名字删（名字唯一，不分外置/离线）
        /hy ls · /hy id <名字>        list / whois 的短别名
  勘探: /lag（无参）＝直接出报告；/lag 30 ＝采样 30 秒；/lag tp 2 ＝传送
  挖掘: /hy clear <x1> <z1> <x2> <z2>（对角两点，选完自动预演）、/hy clear <x2> <z2>（以站位为角点1）、
        /hy clear <边长>（以你为中心的方形）、/hy clear go（= start confirm）、/hy clear dim the_nether
  说明: 名字用空格分隔即为批量。
        没有"手填 UUID"的命令：沿用是自动的（查户口查得到），真要换人用 force —— 这两条已覆盖全部情况。
        README 文首有一张"命令汇总表"，全部命令一页看完。

三阶段配方（沿用社区世吞的作业顺序）：
  阶段1 外圈（内圈各扩 1 格）y = top_y .. top_y+above_height（默认 63..319）清 air
        —— 先清高处，避免上面的方块掉进后面要挖的沟
  阶段2 外圈四条边（1 格宽）y = min_y+1 .. top_y-1（默认 -63..62）填 trench_block（默认沙）
        —— 防爆沟，兜住爆炸与落沙的边界
  阶段3 内圈 y = min_y .. top_y-1（默认 -64..62）清 air
每个批次（默认 4x4 区块 = 64x64 方块）：forceload add → 分层 fill → 区域内 kill → forceload remove

为什么是"内存任务 + tick 驱动"而不是像脚本那样生成数据包：
  · 无需落盘与 /reload；一条命令就能开始
  · preview 能先算给你看；start 必须 confirm
  · stop 立刻停；status 随时问进度；进度同时回聊天与控制台
  · 实体清理用**区域体积选择器**（@e[x=…,dx=…]），不像数据包脚本那样全局 kill @e[type=item]
  · 重启即忘（破坏性任务不持久化，反而更安全）

安全设计：
  · clear.op_level 默认 3（其它命令默认 2；控制台/RCON 是 4）
  · 必须 confirm；preview 不动世界（自检里断言 preview 阶段原版命令轨迹为空）
  · max_side（默认 2048 方块）/ max_volume（默认 5 亿方块）双上限，超限直接拒绝
  · 每条 fill 自动切成 ≤32768 方块（原版上限），分层连续、不重叠、不留空隙（自检有覆盖断言）
  · 批次化 + forceload 加卸载，不长期霸占区块加载
  · 开始/进度/完成/中止全部打控制台审计日志（含发起者与选区）
  · y 范围按该维度真实建筑高度夹取（下界/末地那种 0..255 也正确）

第二块：区块卡顿勘探 + 管理员命令 + UUIDv7 名单管理
---------------------------------------------------------
本版新增两个"纯服务端"能力，并把一类注入隐患修掉。鉴权主链路行为不变（四套自检全过）。

一、区块卡顿勘探（/hy lag …，见 README 第十五章）
---------------------------------------------------------
要点：服务器卡的时候，管理员一条命令就知道"哪个区块在吃 tick"，并点一下直接 tp 到现场。
     不需要客户端 Mod、不需要插件、不发任何网络包。

切点（每类独立降级，缺哪个版本项就那一类是 0，其余照常）：
  ServerLevel#tickChunk(LevelChunk,int)       → 区块 tick（随机刻/冰雪/闪电…）
  ServerLevel#tickNonPassenger(Entity)        → 实体按"实体所在区块"归因
  ServerLevel#tickPassenger(Entity,Entity)    → 乘客实体（船/矿车上的玩家与生物）
  LevelChunk#tickBlockEntities()              → 方块实体（熔炉/漏斗/刷怪笼…）按区块归因
  MinecraftServer#tickServer(BooleanSupplier) → 整服 MSPT 基线（做对比用）

报告：异常区块按 8 邻接合并成"坐标范围"，聊天里每一行都带 ClickEvent(run_command)，
      点一下执行 /hy lag tp <序号>；控制台那一份是同样文字 + [命令: …] 便于复制。
      另给 中位数/P95/单次峰值、维度中文标签、每行的分项明细（区块 tick / 实体 / 方块实体）。

判定：合计 ≥ chunk_lag.flag_threshold_ms(默认 1.0ms)
      或 合计 ≥ 全体中位数 × chunk_lag.flag_relative_factor(默认 6) 且 ≥ 0.15ms。

两种模式：常驻滚动统计（默认开，随时 /hy lag list 看；可 /hy lag off 关）+ 按需扫描
          （/hy lag scan [秒]，到点自动出报告；/hy lag stop 提前结束并出报告）。

"合计会不会重复计"不靠版本假设：运行期探测 tickBlockEntities 是否嵌在 tickChunk 内，
是则从合计里去掉并在报告里写明口径（自检里两条口径都断言过）。

传送：只算落点，执行交给原版 ——
      同维度 /tp @s <x> <地表y> <z>；跨维度 /execute in <维度> run tp …；
      拿不到地表高度时退化为 /execute in <维度> run spreadplayers …（比硬塞 y=100 安全）。
      地表高度用 Level#getHeight(Heightmap.Types.MOTION_BLOCKING, x, z)。

开销：每区块/每实体 tick 两次 System.nanoTime() + 一次无装箱 long 哈希查找 + 几次浮点运算，
      全部在服务端主线程内联执行，不加锁、稳态不分配；常驻窗口有 max_tracked_chunks 上限。

思路来源：分项归因的想法借鉴了 MsptMap（https://github.com/Drizzle379/MsptMap，Fabric Mod，
把每区块 MSPT 画到 Xaero 世界地图上）。**只借鉴思路、未使用其任何代码**；本项目落地方式完全不同
（纯服务端切面 + 命令报告 + 点击传送，不做客户端热力图、不发网络包）。

二、管理员命令（/hy …，见 README 第十六章）
---------------------------------------------------------
接管点：Commands#performPrefixedCommand(CommandSourceStack,String)（控制台 / 游戏内 / RCON 的
唯一汇聚点）。不往 Brigadier 注册节点 ⇒ 不可能与任何原版或插件命令撞名；代价是没有 Tab 补全。
命令根可配置（commands.roots，默认 hy / ha / hyauth，另有 lag 作勘探快捷方式），
权限门槛 commands.op_level（默认 2 = OP；控制台与 RCON 天然满足）。
非本命令根一律返回 false 交给原版（自检里专门断言 /tp 不被吞掉）。

  /hy add ex  <名字> [名字…]        加入 LittleSkin 外置名单（批量＝空格隔开）
  /hy add off <名字> [名字…]        加入离线名单：自动生成 UUIDv7，生成前先查重
  /hy add off <名字> <uuid>         加入离线名单：沿用这条原始记录的 名字+UUID
  /hy off <名字> force              改已有离线玩家：换一个新的 UUIDv7
  /hy off <名字> <uuid>             改已有离线玩家：UUID 改成指定的这个
  /hy del <名字> [名字…]            按名字删除（名字唯一，不分外置/离线）
  /hy list | ls · whois <名字> | id  查看两个名单 / 查这个名字的历史 UUID（查户口）
  /hy reload · status               重读配置并同步常驻采样开关 / 运行状态 + 各切点能力探测
  /hy lag …（或 /lag）：无参=出报告、<秒>=采样、top、tp、here、on|off、stop、clear、status
  /hy clear …：见第一块（空置域挖掘）

命令改配置的方式：读文件 → 改字段 → 写 .tmp → ATOMIC_MOVE 替换 → 立刻 reload
（文件始终是唯一真相，手工编辑与命令改名单不会互相覆盖；gson 保留未定义字段）。

三、UUIDv7 发身份证 + 全量查重（/hy off）
---------------------------------------------------------
UUIDv7（RFC 9562）：48 位毫秒时间戳打头 ⇒ 按 UUID 排序≈按创建时间排序；
同毫秒内的 rand_a 作单调计数器 ⇒ 本生成器产出的 UUID 严格递增，连敲命令也不会乱序。

发之前先扫（这就是"先扫已有 UUID 确认不重复"那一步）：
  ① 配置文件 offline_players（以前发过的身份证）
  ② usercache.json（原版"名字 → UUID"，兼容 uuid / id 两种字段名）
  ③ 存档 <level-name>/playerdata/*.dat、stats/*.json、advancements/*.json
  ④ 原版离线算法 UUID.nameUUIDFromBytes("OfflinePlayer:" + 名字)
新 UUID 还要与扫到的全部已知 UUID 比对一遍（撞车则重新生成）。

拦下逻辑：这个名字若已有身份，默认**拒绝**发新 UUID，并给出
  "沿用旧身份 → /hy off <名字> <旧UUID>" 与 "确实要换 → /hy off <名字> force" 两条明确出路。
（换 UUID = 换人：老存档的背包/成就/统计都挂在旧 UUID 下，不会跟过来。）

四、修掉一个注入隐患（会影响所有辅助类，必读变化）
---------------------------------------------------------
现象：新增的 com.hyauth.agent.util.ChunkLagSampler$2 注入失败
      → NoClassDefFoundError: com/hyauth/agent/util/LongKeyMap$Visitor。
根因：defineClass 在定义某个类的**当场**就解析它的父类与接口，而辅助类之间互相引用；
      jar 条目顺序（大致按字母）不保证被依赖者先定义 ⇒ 顺序一撞就失败。
      旧实现一处失败会中断整批注入 ⇒ 表现为"服务端照常开服、但功能整块静默失效"。
修法（LoaderBridge）：
  · 逐类容错：一个类失败不再连累其它类；
  · 多轮重试（最多 4 轮）：失败的类留到下一轮再试，顺序问题变成非问题；
  · 失败时打印剥掉反射包装后的真实 cause，并汇总失败的类名；
  · 成功日志给出注入数量（本版 53 个），数量明显偏小时就该警惕。
（这个是 verify\loaderiso.ps1 抓出来的：它还原了 Bundler 的"父=platform 的子加载器"拓扑。）

（v1.0.2）外置玩家"自己看不到自己发的消息 + 红字聊天验证错误" —— 已修
---------------------------------------------------------
症状（用户真机）：外置（LittleSkin）玩家发消息后**自己聊天框里不显示**，并弹红字
「聊天验证错误」；别人都看得到；离线名单玩家反而正常。

根因（26.3 原版源码 + 用户现象，两侧都核对过）：
  上一版（v1.0.1）为了让正版客户端不再因为"记账不一致"被踢，把外置玩家的消息**整条**
  换成了"未签名"再广播。副作用是**作者自己那一份也变成了未签名**：

    客户端 PlayerInfo 对每个玩家的校验器，取决于它能不能验证那个人的聊天会话密钥
      · 正版客户端验不了皮肤站签发的密钥 → 对该玩家用 ACCEPT_UNSIGNED → 未签名消息照常显示
      · 外置玩家自己的客户端（authlib-injector 之类）**能**用皮肤站公钥验证自己那把密钥
        → 对自己用"链式校验器" → 未签名消息验不过 →
        ChatListener.handleChatMessageError → 红字 chat.validation_error + 消息不显示

  于是就成了"自己看不到、别人都看得到"。离线名单玩家没有会话密钥，客户端对他们用的是
  ACCEPT_UNSIGNED（enforce-secure-profile=false 时），所以反而正常。

修法：**按接收者分流**（不再是"整条消息一刀切"）。切点从
PlayerList#broadcastChatMessage（对全体一次性改写）换成
ServerGamePacketListenerImpl#sendPlayerChatMessage(PlayerChatMessage, ChatType.Bound)
—— 原版**每个接收者各调用一次**的那个方法：

    发给作者本人 → 原样放行（原版「带签名」消息）
                   · 客户端用自己的公钥验签通过 ⇒ 自己看得到自己发的话
                   · 服务端"已发送签名"账本与客户端记录一致 ⇒ 不会被踢
    发给其他人   → 改用原版自带的「伪装聊天」sendDisguisedChatMessage(Component, ChatType.Bound)
                   · 客户端直接上屏、完全不走签名校验 ⇒ 任何客户端都不会弹「聊天验证错误」
                     （连能验证皮肤站密钥的其它外置客户端也一样）
                   · 服务端不再记账 ⇒ 与客户端记录天然一致 ⇒ 不会被踢

  这不是自创管线：原版 OutgoingChatMessage.create() 对"系统来源的玩家消息"
  （message.isSystem()）走的就是 Disguised 这一支；显示效果与原版聊天一致
  （服务端只送内容，客户端照旧用 ChatType.Bound 拼出 <玩家名> 内容）。

★ 重要更正：外置/离线玩家聊天必须把 enforce-secure-profile 设为 false
---------------------------------------------------------
症状：名单玩家发消息后，**自己聊天框里不显示**，并弹红字「聊天验证错误」；
      而服务端日志里明明有 <玩家> 内容 / [Not Secure] <玩家> 内容（说明服务端已广播）。

根因在**客户端**（26.3 真实字节码，已逐层核对）：

    // net.minecraft.client.multiplayer.PlayerInfo
    private static SignedMessageValidator fallbackMessageValidator(boolean enforceSecureProfile) {
        return enforceSecureProfile ? SignedMessageValidator.REJECT_ALL
                                    : SignedMessageValidator.ACCEPT_UNSIGNED;
    }

    // net.minecraft.network.chat.SignedMessageValidator.REJECT_ALL
    LOGGER.error("Received chat message from {}, but they have no chat session initialized and secure chat is enforced");
    return null;      // → ClientPacketListener.handlePlayerChat 得到 null
                      //   → ChatListener.handleChatMessageError → 红字 chat.validation_error + 丢弃

    // 客户端 ClientPacketListener.handlePlayerChat 关键分支：
    PlayerChatMessage m = info.getMessageValidator().updateAndValidate(message);
    if (m != null) chatListener.handlePlayerChatMessage(...); else chatListener.handleChatMessageError(...);

为什么外置/离线玩家必然命中 REJECT_ALL：
  - 客户端只信任能用 Mojang 服务密钥验证的聊天会话；
  - LittleSkin 账号的密钥由皮肤站签发（客户端验不了）→ 会话被清空；
  - 离线名单玩家根本没有密钥 → 没有会话；
  - 于是客户端用 fallbackMessageValidator(enforcesSecureChat)：
      enforce-secure-profile=true  → REJECT_ALL      → 每条消息都丢
      enforce-secure-profile=false → ACCEPT_UNSIGNED → 未签名消息正常显示

关键点：**这是每个客户端各自按登录包里的 enforcesSecureChat 决定的，服务端切面管不到**。
因此上一版"按玩家豁免 enforce-secure-profile"只能保证服务端收下并广播，
解决不了客户端丢弃。必须改 server.properties 并重启：

    enforce-secure-profile=false

影响：正版玩家（Mojang 签名，客户端能验证）的聊天依旧显示为安全；
      只有客户端验证不了签名的消息标注 [Not Secure]。

★ 本版：离线名单玩家「完全不能聊天」改为按玩家豁免 —— 不需要关闭服务器的全局开关

问题回顾（26.3 真实字节码）：

    // ServerGamePacketListenerImpl 构造器：没有聊天公钥的玩家用这个解码器

        SignedMessageChain.Decoder.unsigned(uuid, () -> server.enforceSecureProfile());
